## 1. Chat request lifecycle (SSE) (`chat-flow`): level 1 of 5: purpose and placement

**Orientation**

- **What it is for.** Handles each chat message: it streams the persona's Claude reply to the browser as it is generated, running safety checks before and after, and saves the exchange.
- **The decision.** One async FastAPI endpoint streams Server-Sent Events from the async Anthropic client. A cheap Haiku hostile pre-check runs first, then retrieval and model choice, then a hard sentence cap. Guardrail and follow-up calls run concurrently after the stream. WebSockets, a blocking request and a worker queue were not chosen; the goals were low latency and a free event loop.
- **Where it lives.**
  - `backend/main.py`: the chat endpoint and its event stream
  - `backend/sentences.py`: sentence capping of the reply
  - `frontend/src/sse.js`: client-side stream parsing
- **Who shaped it.** Yusuf Pisan wrote the first streaming version alone [human] in May 2026, reworked it with an AI co-author [assisted] in June, and hardened it alone [human] in July.

**Question.** Where does the part that streams a persona reply to the browser sit in the life of one chat message? Name the kinds of checks and lookups it relies on before generation, and the work it triggers or hands off to after the reply finishes.

<details><summary>Reference answer (for the grader)</summary>

Before generating it relies on the cheap hostile-message pre-check, usage/rate limits, and persona retrieval/model selection (prompt building). After the stream it launches the guardrail check and follow-up suggestions concurrently, then records the exchange in history/analytics; the browser's stream parser consumes its events. A good answer covers pre-stream gates, the Anthropic streaming call, and post-stream checks plus persistence.

## 2. Cost controls, rate limits and usage metering (`cost-control`): level 1 of 5: purpose and placement

**Orientation**

- **What it is for.** Keeps Claude API spend bounded on a public bot that runs on the owner's personal key, using limits and usage metering.
- **The decision.** Layered controls: per-minute and per-session rate limits, daily exchange caps, token and monthly dollar caps with a login-required threshold, and a bring-your-own-key exemption. Haiku side calls are metered through a context-local tracker. No limits, a paid-only gate and a flat quota were not chosen; the history only says the changes were cost-driven.
- **Where it lives.**
  - `backend/usage_tracker.py`: usage metering and caps
  - `backend/main.py`: rate-limit and cap checks in endpoints
  - `backend/analytics.py`: usage and cost reporting
- **Who shaped it.** Yusuf Pisan built it across three commits from May to June 2026, all with an AI co-author [assisted], including disabling an unmetered daily cron.

**Question.** Beyond the main chat reply, which other parts of the system generate Claude spend that the usage metering has to capture, and who consumes the resulting numbers? What would go unbounded if the metering were missing?

<details><summary>Reference answer (for the grader)</summary>

The auxiliary Haiku side calls (hostile pre-check, retrieval router/cascade classifier, guardrail, follow-ups, history summarisation, FAQ generation) each report usage to the context-local tracker, which forwards to analytics recording. Analytics/usage reporting and the cap checks in the chat endpoints consume these totals; without metering those side calls would be unmetered spend outside token/dollar caps.

Evidence: `backend/usage_tracker.py`, `backend/main.py`, `backend/hostile.py`, `backend/router.py`, `backend/cascading.py`, `backend/guardrails.py`, `backend/followups.py`, `backend/history.py`, `backend/faq_cache.py`

</details>

## 3. Admin dashboard and Persona Fixes loop (`admin-persona-fix-loop`): level 1 of 5: purpose and placement

**Orientation**

- **What it is for.** Lets admins review conversations and rate replies, then turns that feedback into proposed persona edits delivered as a GitHub pull request.
- **The decision.** Feedback goes to Sonnet, which returns full-file rewrites. A background daemon thread does the work while the client polls, because synchronous generation timed out at the edge proxy. Edits are limited to an allowlist of persona files and open a PR rather than pushing to main, so a human approves. Manual edits and a job queue were not chosen.
- **Where it lives.**
  - `frontend/src/AdminPage.jsx`: admin dashboard tabs and polling UI
  - `backend/repo_admin.py`: persona-fix generation and GitHub PR creation
  - `backend/faq_gap_report.py`: FAQ gap analysis
- **Who shaped it.** Yusuf Pisan introduced it in May 2026 with an AI co-author [assisted], then extended the admin page and sessions alone [human] in late May and June.

**Question.** The admin feature that turns reviewer feedback into proposed persona changes sits between several other parts of the system. What does it depend on to run and be authorized, and which part of the system ultimately feels its output once a human approves it?

<details><summary>Reference answer (for the grader)</summary>

It depends on the auth/role capability checks gating admin tabs, stored conversations and ratings, a Sonnet model call, the persona file allowlist, and the GitHub API to open a PR. Once the PR is merged, the persona markdown files in the repo change, which the persona prompt and retrieval system then load for chat replies.

Evidence: `backend/repo_admin.py`, `backend/main.py`, `backend/roles.py`, `frontend/src/AdminPage.jsx`

## 4. Auth and role-based access (`auth-rbac`): level 1 of 5: purpose and placement

**Orientation**

- **What it is for.** Provides optional Google sign-in and roles, so that only users with the right capabilities can reach admin endpoints.
- **The decision.** A Google ID token is exchanged for a JWT. The browser keeps the JWT in localStorage and sends it in the Authorization header, with no cookies, because the Netlify frontend and Render backend are on different origins. Roles live in SQLite and are resolved on every request so changes apply at once. Cookie sessions, an external auth provider and a fixed admin list were not chosen.
- **Where it lives.**
  - `backend/roles.py`: roles and capability mapping
  - `backend/main.py`: login endpoint and capability checks
  - `frontend/src/auth.js`: client token handling
- **Who shaped it.** Yusuf Pisan wrote it alone [human], starting in May 2026 and continuing through the June and July commits.

**Question.** Which other parts of the system rely on the sign-in and role system to decide what a caller may do, and what does the role system itself depend on for identity and for role data?

<details><summary>Reference answer (for the grader)</summary>

Admin endpoints and the admin dashboard tabs rely on role-derived capabilities; email notifications/subscriptions use roles, and usage limits use login status (login-required threshold). It depends on Google for identity verification, the signing secret for the JWT, an environment-configured owner list, and the SQLite database for stored roles.

Evidence: `backend/roles.py`, `backend/main.py`, `backend/notifier.py`, `frontend/src/auth.js`

</details>

## 5. Persona prompt and retrieval modes (`persona-retrieval`): level 1 of 5: purpose and placement

**Orientation**

- **What it is for.** Builds the system prompt from the persona markdown files and tone settings, and chooses how much persona context each request gets.
- **The decision.** Persona knowledge is plain markdown in the repo, so it stays editable through git. Six retrieval modes are selectable at runtime: full, distilled, TF-IDF, Voyage embeddings, Haiku router and cascading. Cascading is the default, and a DB setting overrides env, which overrides the code default. Fine-tuning, one fixed full prompt and a vector DB service were not chosen; the full persona costs about 40K tokens per call.
- **Where it lives.**
  - `persona`: the persona markdown source files
  - `backend/persona.py`: system prompt assembly
  - `backend/cascading.py`: default cascading retrieval mode
- **Who shaped it.** Yusuf Pisan added the persona files alone [human] in May 2026, then built the retrieval modes and the June refactor with an AI co-author [assisted].

**Question.** Which parts of the system consume the assembled persona prompt, and what does the prompt-building part itself depend on to produce it? Name the main upstream inputs and downstream callers.

<details><summary>Reference answer (for the grader)</summary>

Upstream it depends on the persona markdown files (system preamble, knowledge files, distilled version), the tone settings, and the retrieval-mode setting plus helpers (TF-IDF, Voyage embeddings, Haiku router/cascade classifier). Downstream the chat endpoint uses it for each reply, and other features such as the email agent and FAQ generation also use the system or distilled prompt.

Evidence: `backend/persona.py`, `backend/cascading.py`, `backend/main.py`, `backend/email_agent.py`, `backend/rag.py`, `backend/router.py`, `backend/faq_cache.py`

</details>
